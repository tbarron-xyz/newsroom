# attonews Data Storage Strategy (MongoDB)

## Overview
This document outlines the MongoDB data storage strategy for the attonews application. All data is stored in MongoDB using typed collections with appropriate indexes for efficient access and querying. The database name is configured via `MONGODB_DB` (default: `newsroom`).

## Collections and Schemas

### Editor
The editor is a single document with bio, prompt, AI model configuration, and throttling settings.

**Collection:** `editors`
- `_id` - Always `"editor"` (single document)
- `bio` - String containing the editor's biography
- `prompt` - String containing the editor's system prompt
- `modelName` - String containing the default AI model name (legacy field)
- `articleModelName` - String containing the model for article generation
- `eventModelName` - String containing the model for event generation
- `storySelectionModelName` - String containing the model for selecting stories for editions
- `editionSelectionModelName` - String containing the model for selecting editions for daily edition
- `chatModelName` - String containing the model for chat interactions
- `messageSliceCount` - Number containing message slice count for AI processing
- `baseUrl` - String (optional) containing base URL for OpenAI API requests
- `articleGenerationPeriodMinutes` - Number containing article generation period in minutes
- `lastArticleGenerationTime` - Number (optional) containing last article generation timestamp (ms since epoch)
- `eventGenerationPeriodMinutes` - Number containing event generation period in minutes
- `lastEventGenerationTime` - Number (optional) containing last event generation timestamp (ms since epoch)
- `editionGenerationPeriodMinutes` - Number containing edition generation period in minutes
- `lastEditionGenerationTime` - Number (optional) containing last edition generation timestamp (ms since epoch)

**Access pattern:** `findOne({ _id: "editor" })` / `replaceOne({ _id: "editor" }, ..., { upsert: true })`

---

### Reporters
Reporters are stored with their beats, prompts, enabled status, and optional display name. Each reporter has a unique ID.

**Collection:** `reporters`
- `_id` - String: reporter ID
- `id` - String: reporter ID (duplicated from `_id` for type consistency)
- `beats` - Array of strings: the reporter's beat strings
- `prompt` - String: the reporter's system prompt
- `enabled` - Boolean: whether the reporter is enabled
- `displayName` - String (optional): human-readable name for display in UI

**Access pattern:** `find()` for all reporters, `findOne({ _id: id })` for single

---

### Articles
Articles are generated by reporters and stored with metadata including prompts and source messages.

**Collection:** `articles`
- `_id` - String: article ID
- `id` - String: article ID (duplicated from `_id`)
- `reporterId` - String: the reporter ID that generated the article
- `headline` - String: article headline
- `body` - String: article body
- `generationTime` - Number: generation time (ms since epoch)
- `prompt` - String: the full prompt used to generate the article
- `messageIds` - Array of numbers: indices of social media messages used
- `messageTexts` - Array of strings: text content of source messages
- `messageDids` - Array of strings: Bluesky user DIDs for source messages
- `messageRkeys` - Array of strings: Bluesky record keys for source messages
- `modelName` - String: the AI model used
- `inputTokenCount` - Number (optional): input token count
- `outputTokenCount` - Number (optional): output token count

**Indexes:**
- `{ reporterId: 1, generationTime: -1 }` — efficient queries by reporter
- `{ generationTime: -1 }` — global latest articles

**Access patterns:** `find().sort({ generationTime: -1 }).limit(N)` for latest; `find({ reporterId }).sort({ generationTime: -1 })` by reporter; `find({ reporterId, generationTime: { $gte, $lte } })` for time ranges

---

### Events
Events are generated by reporters and stored with facts and metadata.

**Collection:** `events`
- `_id` - String: event ID
- `id` - String: event ID (duplicated from `_id`)
- `reporterId` - String: the reporter ID that generated the event
- `title` - String: event title
- `createdTime` - Number: creation time (ms since epoch)
- `updatedTime` - Number: last update time (ms since epoch)
- `facts` - Array of strings: event facts
- `where` - String (optional): where the event took place
- `when` - String (optional): date/time the event took place
- `messageIds` - Array of numbers (optional): indices of source messages
- `messageTexts` - Array of strings (optional): text content of source messages
- `modelName` - String: the AI model used
- `inputTokenCount` - Number (optional): input token count
- `outputTokenCount` - Number (optional): output token count

**Indexes:**
- `{ reporterId: 1, updatedTime: -1 }` — events by reporter
- `{ updatedTime: -1 }` — latest updated events (global)

---

### Newspaper Editions
Newspaper editions are generated by the editor, containing selected articles.

**Collection:** `newspaper_editions`
- `_id` - String: edition ID
- `id` - String: edition ID (duplicated from `_id`)
- `stories` - Array of strings: article IDs included in this edition
- `generationTime` - Number: generation time (ms since epoch)
- `prompt` - String: the full prompt used to generate this edition
- `modelName` - String: the AI model used
- `inputTokenCount` - Number (optional): input token count
- `outputTokenCount` - Number (optional): output token count

**Index:** `{ generationTime: -1 }`

**Access pattern:** `find().sort({ generationTime: -1 }).limit(N)` for most recent editions

---

### Daily Editions
Daily editions are generated by the editor, containing selected newspaper editions and detailed content.

**Collection:** `daily_editions`
- `_id` - String: daily edition ID
- `id` - String: daily edition ID (duplicated from `_id`)
- `editions` - Array of strings: edition IDs included in this daily edition
- `generationTime` - Number: generation time (ms since epoch)
- `frontPageHeadline` - String: front page headline
- `frontPageArticle` - String: front page article
- `newspaperName` - String (optional): newspaper name
- `topics` - Array of objects with fields: `name`, `headline`, `newsStoryFirstParagraph`, `newsStorySecondParagraph`, `oneLineSummary`, `comments` (optional array of `{ author, content, createdAt, persona }`)
- `prompt` - String: the full prompt used to generate this daily edition
- `modelName` - String: the AI model used
- `inputTokenCount` - Number (optional): input token count
- `outputTokenCount` - Number (optional): output token count

**Index:** `{ generationTime: -1 }`

**Note:** Unlike the Redis backend, `modelFeedbackPositive` / `modelFeedbackNegative` fields are not stored (commented out in the type definition).

---

### Users
Users are stored with authentication and role information.

**Collection:** `users`
- `_id` - String: user ID
- `id` - String: user ID
- `email` - String: user email
- `passwordHash` - String: hashed password
- `role` - String: one of `"admin"`, `"editor"`, `"reporter"`, `"user"`
- `createdAt` - Number: creation timestamp (ms since epoch)
- `lastLoginAt` - Number (optional): last login timestamp (ms since epoch)
- `hasReader` - Boolean: reader access permission
- `hasReporter` - Boolean: reporter access permission
- `hasEditor` - Boolean: editor access permission

**Index:** `{ email: 1 }` (unique)

**Access patterns:** `findOne({ _id: userId })` by ID; `findOne({ email })` by email

---

### KPIs
Key Performance Indicators track AI API usage and costs.

**Collection:** `kpis`
- `_id` - String: KPI name
- `value` - Number: current KPI value

**KPI Names:**
- `"Total text input tokens"` — Total number of input tokens used
- `"Total text output tokens"` — Total number of output tokens used

**Note:** Unlike the Redis backend, the `"Total AI API spend"` KPI is not present, and values are stored as native numbers (not strings). The `$inc` operator is used for atomic increments.

---

### Job Status
Job status tracking monitors the execution state of background jobs.

**Collection:** `job_status`
- `_id` - String: job name
- `running` - Boolean: whether the job is currently running
- `lastRun` - Number (optional): last run timestamp (ms since epoch)
- `lastSuccess` - Number (optional): last successful run timestamp (ms since epoch)

**Job Names:**
- `"reporter"` — Article generation job
- `"daily"` — Daily edition compilation job
- `"newspaper"` — Newspaper edition generation job

---

### Forum
The forum provides a discussion platform with sections, forums, threads, and posts.

#### Forum Sections
**Collection:** `forum_sections`
- `_id` - Always `"sections"` (single document)
- `sections` - Array of `ForumSection` objects: `{ id, title, forums: [{ id, title, description, threadCount, postCount, latestThread }] }`

#### Forum Threads
**Collection:** `forum_threads`
- `_id` - Number: thread ID
- `forumId` - String: parent forum ID
- `title` - String: thread title
- `author` - String: thread author
- `createdAt` - Number: creation time (ms since epoch)
- `replyCount` - Number: number of replies
- `lastReplyTime` - Number: timestamp of most recent reply

**Index:** `{ forumId: 1, createdAt: -1 }`

#### Forum Posts
**Collection:** `forum_posts`
- `_id` - Number: post ID
- `threadId` - Number: parent thread ID
- `content` - String: post content
- `author` - String: post author
- `createdAt` - Number: creation time (ms since epoch)

**Index:** `{ threadId: 1, createdAt: 1 }`

#### Forum Counters
**Collection:** `forum_counters`
- `_id` - String: forum ID
- `threadCount` - Number: total threads in the forum
- `postCount` - Number: total posts in the forum

#### Counters (Sequences)
**Collection:** `counters`
- `_id` - String: sequence name (`"thread_id"` or `"post_id"`)
- `seq` - Number: next available value

Auto-incrementing sequences used with `findOneAndUpdate` + `$inc` to generate thread and post IDs.

---

### Homepage Chat
Homepage chat messages are stored for the global IRC-style chat on the home page.

**Collection:** `homepage_chat_messages`
- `_id` - String: message ID
- `id` - String: message ID
- `senderName` - String: sender display name
- `content` - String: message text
- `timestamp` - Number: timestamp (ms since epoch)
- `type` - String: message type (`"user"` or `"assistant"`)

**Index:** `{ timestamp: -1 }`

**Note:** Unlike the Redis backend (which prunes to 100 entries), MongoDB stores all messages. The application limits retrieval to 50 messages via query limit.

---

### Artifacts
Artifacts are reusable AI processing nodes with prompts, inputs, and output schemas for the flow editor.

**Collection:** `artifacts`
- `_id` - String: artifact ID
- `id` - String: artifact ID
- `type` - String: artifact type (e.g., `"event"`, `"article"`, `"edition"`)
- `inputs` - Array of objects: `{ name, source, type?, filter? }`
- `prompt_system` - String: the system prompt
- `prompt_user_template` - String: the user prompt template
- `output_schema` - String: JSON string containing the output schema
- `output` - Any (optional): the generated output
- `metadata` - Object with fields: `model_name?`, `input_tokens?`, `output_tokens?`, `generated_at?`, `reporterId?`, `status` (`"pending"` / `"generated"` / `"failed"`), `error_message?`

**Indexes:**
- `{ reporterId: 1 }` — artifacts by reporter
- `{ type: 1, createdAt: -1 }` — artifacts by type (note: sorted by `metadata.generated_at` in queries)

**Note:** Unlike the Redis backend, the `output_schema` field IS present in MongoDB (the Redis backend stores only the generated output, not the schema definition).

---

### Personas
Personas are used for dynamic opinion article generation.

#### Dynamic Personas
**Collection:** `dynamic_personas`
- `_id` - Always `"personas"` (single document, replaced on update)
- `data` - Array of `DynamicPersona` objects: `{ display, description, system_prompt }`
- `expiresAt` - Number: expiration timestamp (ms since epoch)

**Index:** TTL index `{ expiresAt: 1 }` with `expireAfterSeconds: 0`

**TTL:** 24 hours (configurable)

#### Classic Personas
Classic personas are not stored in MongoDB. They are sourced from the `CLASSIC_PERSONAS` constant in `ai-prompts.ts` at runtime.

---

### Opinion Articles
Opinion articles are generated by AI personas, providing editorial-style content.

**Collection:** `opinion_articles`
- `_id` - String: opinion article ID
- `id` - String: opinion article ID
- `persona` - String: persona type (one of `"US conservative"`, `"US liberal"`, `"financial globalist"`, `"national populist"`)
- `headline` - String: article headline
- `content` - String: article body
- `generationTime` - Number: generation time (ms since epoch)
- `articleIds` - Array of strings: article IDs referenced
- `modelName` - String: the AI model used
- `inputTokenCount` - Number (optional): input token count
- `outputTokenCount` - Number (optional): output token count

**Index:** `{ generationTime: -1 }`

---

### Ticker
The ticker provides a scrolling news ticker with the latest daily edition summary.

**Collection:** `ticker`
- `_id` - String: ticker document ID
- `id` - String: ticker document ID
- `text` - String: ticker text
- `generationTime` - Number: generation time (ms since epoch)
- `dailyEditionId` - String: associated daily edition ID
- `modelName` - String: the AI model used
- `inputTokenCount` - Number (optional): input token count
- `outputTokenCount` - Number (optional): output token count

**Access pattern:** `find().sort({ generationTime: -1 }).limit(1).next()` for the latest ticker. Single document replaced on update.

---

### Chat Sessions
Chat sessions store temporary AI chat state.

**Collection:** `chat_sessions`
- `_id` - String: session ID
- `data` - Array: chat messages (stored as an array of unknown type)
- `expiresAt` - Date: expiration date

**Index:** TTL index `{ expiresAt: 1 }` with `expireAfterSeconds: 0`

**TTL:** 1800 seconds (30 minutes, configurable)

**Access pattern:** `findOne({ _id: sessionId, expiresAt: { $gt: new Date() } })` — expired sessions are automatically excluded and cleaned up by MongoDB TTL.

---

### App Logs
Application logs for monitoring and debugging.

**Collection:** `logs`
- `message` - String: log message (prefixed with ISO timestamp)
- `timestamp` - Number: log timestamp (ms since epoch)

**Note:** Unlike the Redis backend (which prunes to 500 entries), MongoDB stores all logs without automatic pruning.

---

### Prism
Prism stores daily edition pairs for the prism display feature.

**Collection:** `prism_daily_edition_pairs`
- `_id` - String: pair ID
- `id` - String: pair ID
- `generationTime` - Number: generation time (ms since epoch)
- `leftLabel` - String: label for the left edition
- `rightLabel` - String: label for the right edition
- `left` - Object: full `DailyEdition` document for the left view
- `right` - Object: full `DailyEdition` document for the right view
- `sourcePrompt` - String: the source prompt used
- `leftPrompt` - String: the prompt for the left edition
- `rightPrompt` - String: the prompt for the right edition

**Index:** `{ generationTime: -1 }`

**Pruning:** Application-level — after inserting, the count is checked and older entries beyond 10 are removed.

---

## Collection Naming Conventions
- Use lowercase with underscores for collection names (e.g., `newspaper_editions`, `daily_editions`, `forum_threads`, `prism_daily_edition_pairs`)
- Collection names are typically the plural form of the entity name
- Single-document collections use the entity name (e.g., `editors`, `forum_sections`, `dynamic_personas`)
- Each document uses `_id` as its primary key, matching the entity's `id` field (duplicated for type script compatibility)
- Timestamps are stored as Unix epoch in milliseconds (numbers), not as MongoDB Date objects (except `expiresAt` on TTL collections)

## Data Access Patterns
- **Editor**: `findOne({ _id: "editor" })` / `replaceOne({ _id: "editor" }, ..., { upsert: true })`
- **Reporters**: `find()` for all; `findOne({ _id: id })` for single
- **Latest articles (global)**: `find().sort({ generationTime: -1 }).limit(N)`
- **Articles by reporter**: `find({ reporterId }).sort({ generationTime: -1 }).limit(N)`
- **Articles in time range**: `find({ reporterId, generationTime: { $gte, $lte } }).sort({ generationTime: -1 })`
- **Global time range**: `find({ generationTime: { $gte, $lte } }).sort({ generationTime: -1 })`
- **Single article**: `findOne({ _id: articleId })`
- **Events by reporter**: `find({ reporterId }).sort({ updatedTime: -1 }).limit(N)`
- **Latest events (global)**: `find().sort({ updatedTime: -1 }).limit(N)`
- **Newspaper editions**: `find().sort({ generationTime: -1 }).limit(N)`
- **Daily editions**: `find().sort({ generationTime: -1 }).limit(N)`
- **User by email**: `findOne({ email })` (unique index)
- **User by ID**: `findOne({ _id: userId })`
- **Forum sections**: `findOne({ _id: "sections" })`
- **Forum threads**: `find({ forumId }).sort({ createdAt: -1 }).skip(N).limit(N)`
- **Forum posts by thread**: `find({ threadId }).sort({ createdAt: 1 }).skip(N).limit(N)`
- **Forum counters**: `findOne({ _id: forumId })`
- **Sequences**: `findOneAndUpdate({ _id: name }, { $inc: { seq: 1 } }, { upsert: true, returnDocument: "after" })`
- **Job status**: `findOne({ _id: jobName })` / `updateOne({ _id: jobName }, { $set: ... }, { upsert: true })`
- **KPI**: `findOne({ _id: kpiName })` for value; `updateOne({ _id: kpiName }, { $inc: { value } }, { upsert: true })` for increment
- **Latest ticker**: `find().sort({ generationTime: -1 }).limit(1).next()`
- **Homepage chat**: `find().sort({ timestamp: -1 }).limit(N)` (result reversed to chronological order)
- **Opinion articles**: `find().sort({ generationTime: -1 }).limit(N)`
- **Artifacts**: `find().sort({ "metadata.generated_at": -1 })` for all; `find({ type }).sort({ "metadata.generated_at": -1 })` by type; `find({ "metadata.reporterId": id })` by reporter
- **Dynamic personas**: `find({ expiresAt: { $gt: Date.now() } }).sort({ expiresAt: -1 }).limit(1).next()`
- **Chat session**: `findOne({ _id: sessionId, expiresAt: { $gt: new Date() } })`
- **Logs**: `find().sort({ timestamp: -1 })` for all
- **Prism pairs**: `find().sort({ generationTime: -1 }).limit(N)`

## Index Design & Performance Considerations
- Use connection pooling with `maxPoolSize: 10`, `minPoolSize: 0`
- Implement proper error handling for MongoDB operations
- All queries use covered indexes where possible (time-sorted queries)
- Compound indexes support filtering + sorting in a single index scan
- Unique index on `users.email` enforces email uniqueness at the database level
- TTL indexes on `chat_sessions.expiresAt` and `dynamic_personas.expiresAt` automatically expire stale data
- The `prism_daily_edition_pairs` collection is pruned in application code to 10 entries to prevent unbounded growth
- Monitor collection sizes and query performance as data accumulates
- Consider adding `$limit` to all queries to prevent excessive document retrieval

## Data Persistence
- MongoDB stores data on disk by default with write-ahead journaling
- Configure replica sets for high availability if needed
- Configure backups (e.g., `mongodump`) based on data criticality
- Use MongoDB transactions for operations requiring atomicity across multiple collections

## Security
- Use MongoDB authentication with username/password as specified in `MONGODB_URL`
- Implement proper access controls at the database level
- Encrypt sensitive data (e.g., password hashes) — hashing is handled at the application layer
- Monitor MongoDB logs for security events
- Use TLS for MongoDB connections in production

This strategy provides efficient storage and retrieval of all newsroom data using MongoDB while maintaining clear organization and type safety.
